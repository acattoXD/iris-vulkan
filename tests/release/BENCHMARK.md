# Packaged baseline versus optimized benchmark

Build the disposable probe JAR once and reuse that exact file for both runs. The production baseline must be the immutable friends-alpha JAR; select the candidate JAR separately. Prepare each into a new directory, using the **same closed fixture world and shader ZIP**:

```powershell
python tests/release/prepare_benchmark.py --jar <baseline-or-candidate.jar> --probe-jar fabric/build/probe/iris-native-probe.jar --jdk 'C:/Program Files/Java/jdk-25.0.3' --run-dir build/release-validation/benchmark-baseline --world-source <closed-ultra-world> --shader-pack <ComplementaryUnbound_r5.8.1.zip> --label baseline
```

The helper never starts Minecraft. Run the generated `launch.ps1` serially, with the other test instance closed. The controller uses only `iris.benchmark.*` verification switches; there are no production world/storage-development overrides. It copies the closed world, records hashes of every input file, fixes Ultra's exact sidecar, sets 1280×720, render distance 4, FOV 70, 260 FPS cap, vsync off, and explicitly acknowledges the Vulkan disclosure in this isolated benchmark only. It disables class-load log I/O during measurement; the report records key production/test class hashes instead.

Both preparation and the controller set `inactivityFpsLimit` to `minimized`. Minecraft 26.2 exposes only `MINIMIZED` and `AFK`; it has no `OFF` choice. The minimized setting disables the AFK branches that otherwise impose 30 FPS after 60 seconds and 10 FPS after 10 minutes. A minimized window still receives the engine's 10 FPS limit, so measurement fails if the window is minimized, the live tracker reason differs from `NONE`, or its effective cap differs from 260. Keep foreground/focus conditions consistent between runs; focus is recorded rather than synthesized with fake input.

The default sequence is 15 seconds of warmup, then three 20-second measurement windows separated by one-second unmeasured gaps. `--warmup-seconds`, `--measure-seconds`, and `--repetitions` allow a short plumbing check; do not compare a short check with a full run. The scene uses player position `(0,64,15)`, yaw 180°, pitch 17°, frozen time 4000 and clear weather. The controller does not alter fixture blocks or shader quality.

`evidence/benchmark-report.json` contains per-window p50/p95/p99/max/mean and counts above 33/50/100 ms for frame intervals, runTick wall duration, render-thread CPU time, world CPU submission time, and actual GPU world duration. It also records live limiter state at the start/end and per-window counts of throttle reasons, effective FPS caps, focused/unfocused frames, and minimized frames. Each raw CSV row contains the corresponding cap, reason, focus, and minimized state; collection uses preallocated arrays. GPU measurements use 128 paired query slots and `DeviceInfo.timestampPeriod`; values are checked nonblockingly after at least four frames. No query is reused before its prior result is available. A saturated ring drops samples instead of waiting, and a report needs over 90% GPU coverage per window to pass. No screenshot, staging-buffer copy, storage readback, or GPU fence wait runs inside measurement intervals.

After all intervals, pending queries drain nonblockingly. The probe then captures `benchmark-after.png` and performs the existing fenced Ultra storage/activity verification outside measurements. It writes `benchmark-result.txt` and exits. Compare matching world/shader/options/probe hashes and visually inspect the screenshot before using the timing result. No speedup, bottleneck, or regression claim is made merely because the controller completed. The FPS cap can hide throughput changes; GPU and CPU timings remain separate evidence.

Raw paired samples are written to `evidence/benchmark-samples.csv` after measurement. To compare completed runs, use `python tests/release/compare_benchmarks.py --baseline <baseline-report.json> --candidate <candidate-report.json> --output <comparison.json>`. It rejects mismatched input/profile/probe/GPU hashes, failed runs, or incomplete/throttled limiter evidence before computing median-window timing changes.

Earlier samples recorded with `inactivityFpsLimit:"afk"` can be capped at 30 FPS during these unattended windows and cannot establish a throughput improvement. Existing reports remain unchanged; rerun both artifacts with the same rebuilt diagnostic probe and the corrected controller. The preparer rejects older probe JARs without limiter instrumentation, and the comparator rejects older reports that lack it. Rebuilding a probe for these future comparisons must not replace probe JARs already pinned by running validation profiles.
